dApp integration

One interface,
every Tari wallet.

Your dApp talks to a Tari Ootle wallet through window.tari. The same calls reach the Sapient browser extension, Sapient for Android over WalletConnect, and the Tari Universe web wallet. You never detect which wallet you have: you call methods and feature-detect what they support.

02Quick start

Pick the level of control you want. All three give you a provider with the same request() API.

A ready-made Connect wallet button. It opens the wallet picker, then shows the connected address; clicking it again disconnects.

<!-- 1. Optional: let phone users connect with Sapient for Android (see "Sapient for Android") -->
<script src="/wc-config.js"></script>
<!-- 2. The connector and the picker -->
<script src="https://universe.tari.mw/tari-connector.js"></script>
<script src="https://universe.tari.mw/tari-connect.js"></script>

<!-- 3. The button -->
<tari-connect-button theme="dark"></tari-connect-button>
document.querySelector("tari-connect-button").addEventListener("tari-connect", async (e) => {
  const { wallet, provider, accounts } = e.detail;
  // wallet: "sapient-extension" | "sapient-mobile" | "tari-universe"
  const balances = await provider.request({ method: "tari_getBalances" });
});

Keep your own design; open the picker from it. Show a loading state while it runs: over WalletConnect the user may be approving on their phone.

connectBtn.addEventListener("click", async () => {
  connectBtn.disabled = true;
  connectBtn.textContent = "Connecting…";
  try {
    const { provider, accounts } = await TariConnect.open({ theme: "dark" });
    showApp(provider, accounts[0]);
  } catch (e) {
    if (e.code !== 4001) showError(e.message); // 4001: closed the picker or declined
  } finally {
    connectBtn.disabled = false;
    connectBtn.textContent = "Connect wallet";
  }
});

No picker. Works with the extension and inside Tari Universe; with TARI_WALLETCONNECT set it also pairs with Sapient for Android on the first call.

<script src="https://universe.tari.mw/tari-connector.js"></script>
const [account] = await window.tari.request({ method: "tari_requestAccounts" });
const balances  = await window.tari.request({ method: "tari_getBalances" });
const caps      = await window.tari.request({ method: "tari_getCapabilities" });

Include tari-connector.js always. It supplies the provider inside Tari Universe and over WalletConnect, and stands aside when an extension already owns window.tari.

04Sapient for Android

Opt in, and users without the extension can connect with the Sapient app on their phone. Requests travel end-to-end encrypted over the WalletConnect relay; keys never leave the phone, and every approval happens there.

  1. Optional for production: get a project ID. Without one the connector uses a shared project, which is fine for trying it out. For production, create a free project at cloud.reown.com (Reown runs the WalletConnect relay). The ID is public; it identifies your dApp to the relay and gives you your own quota.
  2. Add your domain to the project's allowed domains. Sapient then shows your site as ✓ Verified on every approval instead of claimed by dApp. A dApp on the shared project always shows as unverified.
  3. Set the config before the connector loads. Put it in its own file if your CSP blocks inline scripts: 
    // wc-config.js
window.TARI_WALLETCONNECT = {
  // projectId: "<your Reown project id>",   optional; a shared one is used if omitted
  network: "mainnet",          // or "esmeralda"; must match the network the phone is on
  // metadata: { name, description, url, icons }   optional; defaults from the page
};
  4. Allow the relay in your CSP, if you send one. connect-src needs: 
    connect-src 'self' wss://relay.walletconnect.org https://rpc.walletconnect.org
  https://pulse.walletconnect.org https://verify.walletconnect.org
  https://verify.walletconnect.com https://echo.walletconnect.com;

What your users see

DesktopA QR code (with a loading shimmer while the pairing link is prepared). They scan it from Sapient's Scan tab.
Phone browserAn Open Sapient button that opens the app directly. No QR code, no copy-paste.
In SapientYour site's name, icon and verification status, then an approval for each request.
WaitingA Check Sapient sheet while a request waits on the phone. After 15 s it offers Pair again.
  • Sessions persist. After a reload the next call reuses the session without a new QR code. If the user removed your site in Sapient, Pair again drops the stale session and shows a fresh code.
  • Network: Sapient refuses a session for a network it isn't on. Set network to match, and listen for networkChanged.
  • Lazy: the WalletConnect code (tari-connector-wc.js, ~160 KB gzipped) loads only on the first call that needs it. Without TARI_WALLETCONNECT nothing about the connector changes.
  • Cancel on the QR dialog or the waiting sheet rejects the call with 4001.

05Wallet picker

Every wallet implements everything above, over every transport, including the transaction-request trio and the private-spend kinds below — except the two GGBP-1 balance-proof methods, which only the web wallet answers (Sapient replies 4200; ggbp1BalanceProof tells you which you have). Check tari_getCapabilities because accounts can differ (a daemon-relayed account has no view secret), not because the wallets do.

Prefer the transaction-request trio. Over WalletConnect the user approves on another device, possibly minutes later. tari_createTransactionRequest persists the request wallet-side, so you can poll the same requestId after a reload; the single-call method loses its result if the page goes away.

07Feature-detect, never wallet-detect

const caps = await window.tari.request({ method: "tari_getCapabilities" });
if (caps.stealthWithdraw) { /* … */ } else { /* offer the plain path */ }

Fields: exactInputSelection, stealthWithdraw, stealthRedeem, stealthRedeemPrivateFee, htlcFund, scriptPathSpend, privateSpend, minimumValuePromise, ownershipProof, walletOwnershipProof, privateBalanceView, privateViewGranted, transactionResultLookup, transactionRequests, walletAddress, dryRunIsLocal, ggbp1BalanceProof (false or the v3 parameters, see L1 balance proofs). If you catch yourself writing if (isSapient), reach for one of these.

08Private spends & proof of funds

Ask for a private spend through tari_createTransactionRequest with kind: "shield" | "unshield" | "sendPrivately" | "withdrawStealthAndExecute" | "redeemStealthOutputAndExecute" | "redeemStealthOutputWithPrivateFee" | "htlcFund" | "htlcClaim" | "htlcRefund". You cannot build a stealth transfer yourself — a raw StealthTransfer instruction passed as { kind: "instructions" } is rejected outright; it needs a balance proof and per-input authorizations only the wallet's own signer can produce.

withdrawStealthAndExecute and redeemStealthOutputAndExecute reveal stealth value onto the transaction's workspace as a Bucket (id 0 — reference it as { Workspace: { id: 0, offset: null } }, a plain integer, not a name) and run your own followUpInstructions against it in the same signed transaction — the difference is only where the value comes from. withdrawStealthAndExecute draws an amount from the connected wallet's own tracked private balance, coin-selected by the wallet. redeemStealthOutputAndExecute spends one specific stealth output — identified by commitmentHex, with its actual revealedAmount — that some other party minted directly to the connected wallet's address (a ballot, a ticket, a voucher): there's nothing to coin-select, you already know exactly which output and how much it's worth. List every other component your followUpInstructions touch in relatedComponents, or the engine rejects the unregistered substate with SubstateNotFound. See llms-full.txt for the full type signatures and a worked example.

Both of those pay their fee from the wallet's revealed balance — fine normally, but if followUpInstructions itself carries something that would deanonymize the wallet if the fee input did (a voting ballot's ranking, say), a revealed fee defeats the whole point: it signs with the wallet's ordinary key, linking the transaction to the account just as plainly as an unshielded send would. redeemStealthOutputWithPrivateFee closes that gap — same as redeemStealthOutputAndExecute, except the fee is also paid from a second stealth UTXO (feeResourceAddress + feeCommitmentHex, a stealth output the wallet already owns and can decrypt, e.g. from its own prior shield). Confirmed live: the resulting transaction's substate diff contains only the two stealth UTXOs and whatever relatedComponents touch — no trace of the wallet's account address. maxFee is still revealed publicly as a flat amount (bucket-paid fees have no refund destination), and the result carries feeChangeCommitment — the fee UTXO's unspent remainder, which you must track yourself to fund a later call the same way.

shield and sendPrivately accept minimumValuePromise — a public, permanent claim baked into the new output's own range proof that it's worth at least that much. That output becomes a self-contained, non-interactively verifiable proof of funds:

// Prove this wallet can cover 100000, without revealing what it actually holds.
const { requestId } = await window.tari.request({ method: "tari_createTransactionRequest", params: {
  kind: "shield", resourceAddress, amount: "100000", minimumValuePromise: "100000",
}});
// ...poll tari_getTransactionRequest until approved, then tari_submitTransactionRequest.
// The result carries `substateId` — put that in your link.

// Anyone verifies it — no wallet, no signature, no live session:
const substate = await window.tari.request({ method: "tari_getSubstate", params: { substateId } });
// -> read `minimum_value_promise` off the output, and confirm the substate is still unspent.

Three things to design around: the disclosure is public and permanent for as long as the output exists, not just to whoever the proof was for; it proves one output, not a whole balance (shield the full amount into one output first to prove total spending power); and spending the output destroys the proof — a verifier must re-check the substate is still unspent at the moment they care, not merely that it once existed.

09Ownership proofs — who's showing you the link

A minimumValuePromise link is a bearer artifact: it proves an output exists and is unspent, not who is presenting it. Anyone who obtains the substateId — a screenshot, a forwarded link — can present it identically. Closing that gap needs a signature over a challenge the verifier generated themselves:

// The verifier makes this up and gives it to the prover through their own channel:
const challenge = "prove-carol-" + new Date().toISOString() + "-" + crypto.randomUUID();

// The prover's wallet signs it:
const { publicKey, publicNonce, signature } = await window.tari.request({
  method: "tari_signOwnershipChallenge",
  params: { resourceAddress, substateId, challenge },
});

// The verifier checks the response against the substate's OWN on-chain key —
// never against `publicKey` at face value, since anyone can self-report any key:
const substate = await window.tari.request({ method: "tari_getSubstate", params: { substateId } });
const authKey = substate.substate.Utxo.output.auth.Key;
// authKey === publicKey, and (publicNonce, signature) verify against it and `challenge`
// via standard Ristretto/Schnorr verification — see the reference implementation below.

The bytes actually signed are not challenge alone — the wallet wraps it under a domain tag (com.tari.paylink.ownership_proof) disjoint from real transaction signing (com.tari.ootle.transaction), which is exactly why there's no way to ask for a raw signature over an arbitrary message instead: doing that naively risks a signature that's replayable as spend authorization. A static or reused challenge proves nothing about when — always generate a fresh one per check.

Working reference implementation, challenge/response UI included, at /paylink — its verify page runs the Ristretto/Schnorr check entirely client-side against public on-chain data, no wallet required to check someone else's proof.

Proving you hold a wallet address, generically

tari_signWalletOwnershipChallenge is the same idea with no output involved — it proves the connected account holds its own otl_… wallet address, full stop:

const { walletAddress, publicNonce, signature } = await window.tari.request({
  method: "tari_signWalletOwnershipChallenge",
  params: { challenge: "prove-carol-2026-09-03-8f2a1c" },
});

Signs with the account's own persistent owner key, under its own domain tag (com.tari.paylink.wallet_ownership_proof) — deliberately different from both real transaction signing and the per-output proof's domain, so a signature can never be mistaken for the wrong kind of claim. A verifier decodes the owner key from the address they already have in mind (parseOotleAddress, no network call needed) and checks against that — never against walletAddress as returned. Requires capabilities.walletOwnershipProof. The /paylink page's "Prove you hold a wallet address" / "Check a wallet ownership proof" widgets are a working example of both sides.

L1 balance proofs (GGBP-1 v3) — experimental, Esmeralda only

The web wallet can prove that it holds at least some amount of L1 XTM, without revealing the exact amount and without moving anything. The proof is a GGBP-1 v3 aggregate-threshold proof over the wallet's own L1 outputs: a Bulletproofs+ range proof that their summed commitments reach your threshold, plus Schnorr signatures from each output's script key and from a per-site subject key, all bound to your challenge. Check capabilities.ggbp1BalanceProof first: false, or { protocolVersion: 3, network: "esmeralda", maxOutputs: 16, maxProofBytes: 8192 }.

// 1. Once per user: ask for this wallet's subject key for your site (the user approves).
const subject = await window.tari.getBalanceProofSubject();
// { protocol: "ggbp1", version: 3, network, genesisHash, originHash,
//   subjectPublicKey, commitmentGeneratorFingerprint }  (hex)

// 2. Your server issues a 223-byte challenge (fresh nonce, threshold, expiry, gate ids):
//    "GGBP1" ‖ 0x03 ‖ network ‖ genesisHash ‖ originHash ‖ gate_id(16) ‖ le64(gate_config_version)
//    ‖ subject_id(16) ‖ subjectPublicKey ‖ le64(threshold µT) ‖ nonce(32) ‖ le64(expires_at)
//    ‖ commitmentGeneratorFingerprint                       — sent as unpadded base64url

// 3. The wallet shows the user exactly which outputs it will disclose.
const { response } = await window.tari.requestBalanceProof(challenge);

// 4. Your server: parse the GGBP1R v3 response, compare every challenge field with what it
//    issued, run the v3 verifier, then check each disclosed output on chain (exists, unspent).
  • It proves the cryptography, not that the money is still there. The outputs could be spent a block later, and the verifier cannot tell a real output from a made-up one. Check every disclosed output hash against the chain yourself, and revalidate before you rely on it again.
  • It is not anonymous. The response names the outputs' hashes and commitments: you can find them on chain and see they share an owner. The exact amounts stay hidden.
  • originHash is SHA-256("GGBP1/origin" ‖ origin) for your page's exact origin; a challenge for any other origin, network, subject key or an expired one is refused with -32603.
  • A user declining and "this wallet can't reach the threshold" both reject with 4001, so you cannot probe balances. The wallet also allows one open request per site and 10 per hour.
  • Thresholds come from your server, never from user input on the page. Version 2 of GGBP-1 is unsafe and is never produced.

Full encodings, the subject-key derivation and what the wallet checks: WALLET_INTEGRATION.md.

10Resource types — what "private" means depends on the resource

ResourceType (Fungible | NonFungible | Confidential | Stealth) is fixed per-resource at creation, not a wallet or dApp choice. Everything above works for any Stealth-type resource, not just XTR — nothing in the API is XTR-specific.

  • Fungible / NonFungible — plain, public on-chain data. No wallet call needed to read them: derive the component address from the wallet address and query the indexer's vaults directly. Combine with tari_signWalletOwnershipChallenge to attach "and this is verifiably them" to an otherwise fully public lookup — see /paylink's "Look up public holdings" (no signature) and "Check a wallet ownership proof" (adds the identity check).
  • Stealth — everything else on this page.
  • Confidential — a different privacy mechanism: vault-based, ElGamal-encrypted to a resource-specific view key. A closed, reveal-to-one-party model, not a public floor proof — there is no minimumValuePromise equivalent for it, and this API surface doesn't expose deposit/withdraw or balance-decryption for Confidential vaults.

14Being embeddable

Tari Universe runs dApps in a cross-origin iframe. If you send X-Frame-Options or a CSP that excludes it, the wallet falls back to opening you in a tab. To allow embedding:

Content-Security-Policy: frame-ancestors 'self' https://universe.tari.mw;

Pitfalls that cost real time

  • An inline TARI_WALLETCONNECT script is silently blocked by a strict CSP. The connector then never offers Sapient for Android and the picker shows only the extension. Load the config from a file on your own origin.
  • A QR code that never connects is usually connect-src. The pairing link is made locally, but the relay socket is blocked; your console shows the CSP violation.
  • Don't leave a dead Connect button while the user approves on their phone. Disable it and show progress until TariConnect.open() settles, or the page looks broken while the real action is on another device.
  • Wallet addresses are not component addresses. Users hold otl_esm_1…; instruction arguments need component_…. Passing the wrong one fails deep in deserialization as "data did not match any variant of untagged enum TransactionInput", naming neither field nor reason.
  • An account is created on first funding. Depositing into one that has never received anything aborts with OneOrMoreInputsNotFound; creating one that exists rejects with "is already UP and conflicts with an existing output". Check, then create only if absent.
  • Do not pin cached substate versions. Let the wallet resolve them, or you get Lock failure: Substate …:N is not found or DOWN.
  • Amounts are strings or bigints, never JS numbers — they exceed Number.MAX_SAFE_INTEGER. Divide by 10 ** divisibility to display; never assume 6.
  • A Stealth resource holds two balances. amount is the revealed side, confidentialAmount the stealth side. A revealed balance of 0 does not mean empty.
  • A proof-of-funds link doesn't prove who's showing it to you. Check that with tari_signOwnershipChallenge against a challenge you generated, verified against the substate's own auth.Key — never against a public key the other party supplies about themselves.
